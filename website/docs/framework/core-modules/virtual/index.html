Virtual Lists

Render long lists, tables, grids, and galleries efficiently with windowed scrolling.

Overview

When a list, table, or gallery grows past a few hundred items, rendering them all up front becomes slow — with initial paint stalls, scrolling stutters, and climbing memory. The Virtual Lists module solves this by only mounting the items currently visible in the scroll viewport, plus a small overscan buffer for smooth scrolling. A collection of ten thousand items can keep just twenty or so in the DOM at any time while the user scrolls through smoothly.

Items render with the layout you already use — a stacked list, a native <table>, a CSS grid, a flex-wrap gallery, or a masonry wall — so virtualizing doesn't change your markup or break column alignment, sticky headers, or shared cell styling.

Each item is measured as it renders, and again whenever its size changes, so tall items (multi-line text, embedded media, expanded details) coexist with short ones without configuration. There's no fixed-size requirement.

Virtualization is a rendering optimization, not a data-fetching one. The data array stays in memory, and only its DOM representation is windowed. To load a large table a page at a time as people scroll, pair it with a paged source and the virtual-end event.

SEO & AEO (Answer Engine Optimization): virtualized content is rendered client-side at scroll time, so it isn't visible to search engines or AI crawlers by default. Virtualization is best applied to interactive data like dashboard content, where discoverability isn't the goal.

Setup

Virtual loads automatically when the page uses x-virtual or $virtual, or can be selectively loaded.




<script src="https://cdn.jsdelivr.net/npm/mnfst@latest/lib/manifest.min.js"></script>


<script src="https://cdn.jsdelivr.net/npm/mnfst@latest/lib/manifest.min.js"
    data-modules="virtual"></script>

Basic Usage

Wrap an x-for template in a scrolling container marked with x-virtual. The container needs a bounded height like a pixel value, percentage, viewport unit, or flex layout in order to support a scroll viewport.



<div x-data="{ team: /* 500 entries */ }">
    <div x-virtual class="h-[300px] overflow-auto">
        <template x-for="member in team" :key="member.id">
            <div>
                <p x-text="member.name"></p>
                <small x-text="member.role"></small>
            </div>
        </template>
    </div>
</div>

Five hundred items are in the array, but only the visible window is rendered as you scroll. The module sets overflow: auto on the container automatically if it isn't already scrollable.

The module moves the template's x-for and :key to data-virtual-for and data-virtual-key, so Alpine doesn't double-render them and a prerendered page can run the list again on load. The template may be nested — for example inside <table><tbody> — and the module will still find it. If the container holds more than one x-for template (a header row built from data, say), mark the rows template with data-virtual. Without the marker, the first template outside <thead> and <tfoot> is used, and the console warns when that choice was down to order alone.

Without :key, the key defaults to item.id, so items without an id don't render; give each item a stable key. The x-for can name the item alone (row in items) or the item and its index ((row, i) in items or row, i in items), and :key can use both names. A form x-virtual cannot run, such as destructuring (({ id, name }, i) in items), is not virtualized: the list renders in full through the normal x-for and the console shows a warning.

Layout

The same x-virtual adapts to whatever markup fits your data — a native table, a CSS grid, a wrapping gallery, or a masonry wall. The module detects the layout automatically; masonry is the one mode you set explicitly.

Table

Put x-virtual on the scroll container and let the x-for template live inside <tbody>. Columns align across rows and <thead> can be sticky, exactly as in a normal table.



<div x-virtual class="h-[300px] overflow-auto">
    <table class="table-fixed w-full">
        <thead>
            <tr><th>Name</th><th>Email</th><th>Role</th></tr>
        </thead>
        <tbody>
            <template x-for="user in $x.users" :key="user.id">
                <tr :class="user.id % 2 ? 'bg-surface-1' : ''">
                    <td x-text="user.name"></td>
                    <td x-text="user.email"></td>
                    <td x-text="user.role"></td>
                </tr>
            </template>
        </tbody>
    </table>
</div>

Grid

    <div class="grid-header">
        <div>Name</div><div>Email</div><div>Role</div>
    </div>
    <template x-for="user in $x.users" :key="user.id">

            <div x-text="user.name"></div>
            <div x-text="user.email"></div>
            <div x-text="user.role"></div>

Gallery

A gallery packs many items per line. The module auto-detects a flex-wrap container; for a CSS grid, add mode: 'gallery' so it isn't read as a table. Either way only the visible items mount — ragged widths and heights are fine. Seed estimate with an approximate item size for a steadier first paint.



<div x-virtual="{ estimate: { width: 160, height: 120 } }"
     class="flex flex-wrap content-start gap-2 h-80 overflow-auto">
    <template x-for="tile in $x.tiles" :key="tile.id">
        <div class="center rounded text-white text-sm font-semibold"
             :style="`width: ${tile.w}px; height: ${tile.h}px; background: ${tile.color}`"
             x-text="'#' + tile.id"></div>
    </template>
</div>

Masonry

Masonry packs items of independent sizes into the shortest column — the layout where the occasional showcase item spans extra width or height. Set mode: 'masonry' and either a columnWidth or a fixed columns count.



<div x-virtual="{ mode: 'masonry', columnWidth: 220, gap: 12, span: block => block.span, height: block => block.height }"
     class="relative h-96 overflow-auto">
    <template x-for="block in $x.blocks" :key="block.id">
        <div class="center rounded text-white text-sm font-semibold"
             :style="`height: ${block.height}px; background: ${block.color}`"
             x-text="'#' + block.id"></div>
    </template>
</div>

Masonry positions items absolutely and sizes the container for you. Pass a height function (matching the item's own height) for the smoothest first paint, since the layout can then be computed before anything is measured.

Property Type Default Description
columnWidth Number — Target column width in px; the column count is derived from the container width.
columns Number 3 A fixed number of columns. Use this or columnWidth; with neither, masonry uses 3 columns.
gap Number CSS gap Pixel gap between items.
span Function () => 1 Maps an item to how many columns it spans, for wide showcase items.
height Function — Maps an item to its height in px. Supplying it skips measurement; otherwise each item is measured when it renders and whenever its size changes.

Customization

Pass options as an object expression on the directive.

Property Type Default Description
estimate Number or { width, height } 50 (120 wide) Initial size for unmeasured items. A closer estimate produces less scroll-position drift on first paint. Galleries and masonry accept an object to seed both axes.
overscan Number 3 Items (or lines) to render above and below the visible window. Higher values smooth out fast scrolling at the cost of more DOM.
mode String auto How items fill lines: rows (one per line — lists, tables, grids), gallery (many per line — flex-wrap or CSS grid), or masonry. Auto-detected from the container for all but masonry, which is always explicit.
recycle Boolean false Hand rows leaving the window to rows entering it instead of rebuilding them. See Reusing Rows. 
<div x-virtual="{ estimate: 80, overscan: 5 }" class="h-[600px] overflow-auto">
    <template x-for="item in $x.products" :key="item.id">
        <div>...</div>
    </template>
</div>

Without these options the defaults will work for most uniform collections. Tune estimate higher when items are tall (cards, images), and raise overscan if you see brief blank flashes during fast wheel-scrolling.

Mixed Sizes

Items with variable content like multi-line descriptions, embedded images, or expanded details work without any extra configuration. Each item is measured when it renders and measured again whenever its size changes later, such as an image finishing loading, markdown rendering or the container being resized, and the scroll offsets adjust to its actual size. There is no fixed-size requirement.



<div x-virtual class="h-[600px] overflow-auto">
    <template x-for="log in $x.logs" :key="log.id">
        <div>
            <span x-text="log.time"></span>
            <span x-text="log.level"></span>
            <span x-text="log.message"></span>
        </div>
    </template>
</div>

The module never moves the scroll position itself unless you ask it to with scrollToIndex or scrollToKey, so scrollTo() and scrollIntoView() run to the end and momentum scrolling isn't interrupted. When a rendered item above the visible area grows, the browser's own scroll anchoring keeps the view in place, where the browser supports it. To scroll to an item that isn't rendered yet, see Scrolling to an Item.

Scrolling to an Item

Items outside the window are not in the page, so scrollIntoView() can't reach them. Use $virtual instead. Inside a list, $virtual is that list. From anywhere else, pass the list's id or element, as in $virtual('people') or $virtual($refs.list).



<div x-data="{ jump: 0 }">
    <input type="number" x-model.number="jump" aria-label="Row number">
    <button @click="$virtual('people').scrollToIndex(jump, { behavior: 'smooth' })">Go</button>
    <div id="people" x-virtual class="h-[300px] overflow-auto">
        <template x-for="person in $x.people" :key="person.id">
            <div x-text="person.name"></div>
        </template>
    </div>
</div>

scrollToIndex(index, options) scrolls to the item at a position in the data. The index can also be text made only of digits, as x-model gives without .number. scrollToKey(key, options) scrolls to the item whose :key is key. Keys are compared exactly, so '42' does not match 42.

Both return a promise that resolves with the item's row element once the row is where you asked. Rows between here and there have not been measured yet, so the module corrects the position as they render. If rows near the item then change size, for example as images load, the list keeps the item in place until nothing has changed for a moment, for up to three seconds. If sizes never stop changing, the promise resolves after about a second and a half of trying, as close as it got.

Property Type Default Description
align String 'start' Where the item lands: start, center, end, or nearest (only scrolls if the item isn't fully visible).
behavior String instant 'smooth' animates the scroll. People who prefer reduced motion get an instant jump.
offset Number 0 Extra pixels to keep clear at the aligned edge (no effect with center). The list's CSS scroll-padding is respected too, in any unit including calc(). This is the simplest way to clear a sticky header.

Scrolling never moves focus. To focus the row afterwards, use the element the promise gives you. The row is already in place, so focusing it doesn't move the list:

<button @click="const row = await $virtual('people').scrollToKey(42, { align: 'center' }); if (row) { row.tabIndex = -1; row.focus() }">
    Show #42
</button>

Scroll Details

  • The promise resolves with null when there is no item at that index or key, when a different call replaces it, when the item leaves the data, or when the list is scrolled some other way before the item is in place. That other way can be the person (wheel, touch, scroll keys on the list or with nothing focused), find in page, or your own code. Keys pressed in other widgets or scroll areas don't count. But if such a key makes the browser itself scroll the list, that scroll still ends it: for example PageDown in a field inside a row, or the caret being scrolled into view. The console warns once about a missing item or an index that isn't a whole number.
  • While the list is still moving to the item or keeping it in place, a scroll from somewhere else that goes straight to the very end of the list in one step, such as your own code setting scrollTop to the bottom, looks the same as the browser trimming the scroll position while rows resize. The list then puts the item back. A scroll that stops anywhere short of the end ends it as usual, and wheel, touch and scroll keys on the list always end it.
  • Calling again with the same item and options while a scroll is running joins it. Once it has landed, the same call lands it again if it has moved.
  • The item is followed by its key, so items added or removed elsewhere during a smooth scroll don't change where it lands.
  • A list hidden with x-show scrolls once it is shown, and a list hidden partway through keeps its promise waiting until it is shown again. Closed dialogs, menus and tab panels don't build their contents until they first open, so a call made before then finds no list: it warns and resolves with null. Call it after opening the container.
  • Only the list scrolls. If the list itself is off screen, scroll the page to it first.
  • In a list that snaps vertically (scroll-snap-type on the block axis), the scroll is always instant. The browser then snaps, and the row ends up where the snap puts it. The promise resolves with the row if it is visible, otherwise null; this happens occasionally with end and nearest.
  • From a parent's x-init, the list may not be ready yet: call it inside $nextTick.
  • $virtual looks lists up by id in the page, so content teleported out of a list must name the list by id, and ids must be unique.
  • Lists scaled with CSS zoom aren't supported.

Dynamic Data

Point the template's x-for at any reactive source — a local or cloud data source through $x, or plain Alpine state — and the window stays in sync. Adds, deletes, sorts, and filters update the visible items automatically, and items re-bind by key, so reordering the data never scrambles their content.

That makes virtualization a natural pair with $search and $query: wire a search input to $x.<source>.$search() and the list re-renders against the filtered results without rebuilding the whole DOM.



<div x-data="{ term: '' }">
    <input type="text" placeholder="Filter products..." aria-label="Filter products" x-model="term">
    <div x-virtual class="h-[600px] overflow-auto">
        <template x-for="product in $x.products.$search(term, 'name')" :key="product.id">
            <div>
                <p x-text="product.name"></p>
                <small x-text="'$' + product.price"></small>
            </div>
        </template>
    </div>
</div>

Loading More at the End

When the last item in the data is rendered, the x-virtual element fires a virtual-end event (once for each length the data reaches). Use it to load the next page:

<div x-virtual class="h-[600px] overflow-auto" @virtual-end="$x.contacts.$more()">
    <template x-for="contact in $x.contacts" :key="contact.$id">
        <p x-text="contact.name"></p>
    </template>
</div>

event.detail.length is the number of items in the data when it fired.

Inside Menus and Dialogs

x-virtual works inside popover menus, dialogs and tab panels. The list measures itself when its container is shown, so nothing special is needed — give the x-virtual element a bounded height as usual and place it inside the menu.



<div x-data="{ countries: /* 300 entries */ }">
    <button x-dropdown="country-menu">Country</button>

    <menu popover id="country-menu">
        <div x-virtual class="h-64">
            <template x-for="country in countries" :key="country.id">
                <li x-text="country.name"></li>
            </template>
        </div>
    </menu>
</div>

A closed menu's contents are not initialized until it opens, so the virtualized list costs nothing while the menu is closed and renders only its visible rows once it opens.

Reusing Rows

By default, a row that scrolls out of the window is removed, and a new one is built for each row scrolling in. With recycle: true, the leaving row's elements are handed to an entering row and given its item instead. This can make large jumps through the list noticeably faster when rows are heavy. Small scroll steps and light rows gain little.

<div x-virtual="{ recycle: true }" class="h-[600px] overflow-auto">
    <template x-for="task in $x.tasks" :key="task.id">
        <div x-data="{ open: false }" @manifest:virtual-recycle="open = false">
            <p x-text="task.title"></p>
            <button @click="open = !open">Notes</button>
            <p x-show="open" x-text="task.notes"></p>
            <button x-dropdown="`task-menu-${task.id}`">Actions</button>
            <menu popover :id="`task-menu-${task.id}`">
                <li x-text="`Open ${task.title}`"></li>
            </menu>
        </div>
    </template>
</div>

Rows Follow Their Item

A reused row must be a function of its item. Everything bound to the item updates: text, attributes, classes, x-show, x-if, nested x-for and x-model, and click handlers act on the new item. These do not reset:

  • Row-local x-data state, and values copied from the item when the row started.
  • x-init, which runs once per row element, not once per item.
  • DOM state with no binding: text typed into a field without x-model, an unbound checkbox, an inner scroll position, a playing video.

To reset row-local state, listen for manifest:virtual-recycle on the row's root element, as in the example above. The event doesn't bubble, so a listener on an inner element never hears it. It fires after the row has updated to its new item, $event.detail is { key, index }, and it never fires for a newly built row.

Rows That Are Rebuilt

Some rows are rebuilt as usual instead of being reused, so nothing a person is using changes under them:

  • A row that holds focus.
  • A row with an open popover, <details> or <dialog>.
  • A row with a trigger marked aria-expanded="true" (as x-dropdown sets it) for a menu or popover open elsewhere, or that is the trigger of an open context menu.
  • Any of the above in content the row teleports elsewhere with x-teleport.
  • A row whose root is a <template>.

Lists whose rows use x-transition don't reuse rows at all, and masonry layouts never do.

Things To Know

  • The console warns when rows use x-transition (reuse is off for that list), and when rows use x-init without a manifest:virtual-recycle listener on the root.
  • An image shows its previous picture until the new src loads.
  • .once handlers don't fire again for the new item.
  • CSS transitions on bound classes can play when a row changes item.
  • The option is read when the list starts, so changing it later has no effect.
  • A per-row menu needs a template-literal id, as in the example, so the trigger follows the row's item. See dropdown templating.
