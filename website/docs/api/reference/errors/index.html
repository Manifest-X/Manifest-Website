Errors

What an error looks like, what each code means, and how to retry safely.

Error Shape

Every error has the same shape. message is written for a person, so branch on error instead.

{
  "error": "unauthorized",
  "message": "That API key is not recognised.",
  "request_id": "…"
}

Quote the request_id when you contact Manifest. Some errors add a property:

  • field names the input at fault, such as "articles[1].slug" or "files[0].path".
  • live_deployment_id comes with base_mismatch, so you can reapply your change on it.

Upload and status URL errors carry error and message, but no request_id. Any path outside /v1/* answers 404 not_found with "No such API route." A rare unexpected failure can answer 500 without a JSON body. Retry it like any 5xx.

Common Problems

Symptom Likely cause Fix
401 unauthorized on every request The header isn't Authorization: Bearer mnfst_api_…, or it sends a project key (mfst_…) instead. Send an API key from the dashboard's API page.
A browser fetch fails with a CORS error The API refuses browsers. Call it from your server.
404 not_found for a project in your dashboard The path is missing /v1, the id is wrong, or the project belongs to another account. Check the URL, and the id from GET /projects.
403 forbidden on a team project You're a member of it, not its owner or an admin. Ask the owner for the admin role.
409 subdomain_taken on create Another project, perhaps someone else's, has that subdomain. Pick another, or leave subdomain out.
409 source_id_conflict on create The project exists under that source_id with another name. Look it up instead of creating it.
403 project_cap_reached The free allowance's two projects are in use. Delete a test project, or talk to us about Enterprise.
402 pro_required Rollback and inviting editors are part of Pro. Upgrade the project in the dashboard. On Free, publish the earlier version again.
An address says "This site hasn't been published yet." Nothing is live on that environment. Publish to staging, then promote.
Production doesn't show your change Updates land on staging. Check staging, then promote.
An old version still shows The browser kept the page. Reload. Pages are cached for up to a minute.
"No Manifest site is configured for this address." The custom domain isn't active, was removed, or its project was deleted. Check the domain's status.
An upload's status stays ingesting Each poll moves the publish forward. Keep polling status_url until done or error.
429 A rate or daily limit is reached. Wait the seconds in Retry-After. See Limits.

409 live_moved Production isn't serving your expect_live deployment any more, so nothing was promoted. The message names what is live. Check deployments before retrying.
410 project_deleted The project was deleted. The message says until when Manifest can restore it. See Projects.
410 expired The upload URL expired or was already used. Start a new publish.
413 too_large The zip is over 80 MB, a file is over 25 MB, or the unzipped build is over 250 MB.
413 too_many_files The zip holds more than 10,000 files.
413 payload_too_large A content or file update body is over 12 MB.
413 file_too_large A file update's file is over 8 MB. Publish it in a zip.
413 deployment_too_large The updated project would pass 250 MB or 10,000 files.
422 invalid_content A content slug, size, theme value, or page field is invalid. field says which.
422 not_api_project Content only works on projects created through the API. Publish a zip instead.
422 invalid_path A file update path is unsafe, private, written by Manifest, compiled, or listed twice. field names it.
422 invalid_file A change needs exactly one of content, content_base64, or delete, or its base64 is invalid.
422 file_not_found A delete names a file that isn't on staging.
422 no_index The update would leave the project without index.html.
422 hostname_reserved The hostname is on a Manifest domain, such as manifestx.ai.
422 subdomain_reserved That subdomain is reserved, such as login or billing.
422 idempotency_key_reused The key was already used for another body, endpoint, or project. Use a new key.
422 invite_failed Manifest's team service refused the address. The message says why. Fix it rather than retrying.
429 rate_limited Too many requests or writes. Wait the seconds in Retry-After. On the status URL there's no Retry-After: wait a minute.
429 mint_limit 20 keys were created in the last 24 hours. Wait the seconds in Retry-After.
429 invite_limit The project's 50 invites for today are used. Wait the seconds in Retry-After.
429 publish_limit_reached A Free project's daily publish limit is reached. Wait the seconds in Retry-After.
500 ingest_failed Content failed before going live, and what was live is unchanged. Retry.
500 update_failed A file update failed. The message says whether staging is unchanged, or to check deployments first.
502 domain_attach_failed The domain couldn't be added. Check the hostname, then retry.
503 update_timed_out Storing the files took too long, and staging is unchanged. Retry, or send fewer files.
503 promote_failed The promote couldn't finish, and production is unchanged. Retry shortly.
503 publish_unavailable A publish couldn't be started. Retry shortly.
503 template_unavailable The docs template couldn't be loaded. Retry shortly.
503 domain_status_unavailable The domain status couldn't be read just now. Retry shortly.
503 domains_unavailable Custom domains are briefly unavailable. Retry later.
503 membership_unverified Your role on a team project couldn't be checked. Nothing was done. Retry.
503 team_unavailable The project's team couldn't be reached. No one was invited or removed. Retry.
503 webhooks_unavailable Webhooks are briefly unavailable. Retry later.
503 idempotency_unavailable Idempotent requests are briefly unavailable. Retry later. Retrying without the header loses its duplicate protection.

Retrying

  • 400 and 422: fix the request. Sending it again unchanged gives the same answer.
  • 409: retry the _in_progress codes shortly. The others need a change first.
  • 429: wait the seconds in Retry-After, then retry.
  • 5xx: retry with the same Idempotency-Key. Failures are never stored, so the retry runs again.

Two 5xx codes need a check first. When update_failed says the update may or may not be live, check deployments. On 502 domain_attach_failed, check the hostname.

Idempotency

Send an Idempotency-Key header so a retried request never runs twice.




curl -X POST https://api.manifestx.dev/v1/projects/proj_…/promote \
  -H "Authorization: Bearer $MANIFEST_ACCOUNT_KEY" \
  -H "Idempotency-Key: help-center-sync-0193-promote"


const res = await fetch('https://api.manifestx.dev/v1/projects/proj_…/promote', {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${process.env.MANIFEST_ACCOUNT_KEY}`,
    'Idempotency-Key': 'help-center-sync-0193-promote',
  },
})
  • Which requests. Every POST, PATCH, and DELETE accepts it, such as content, file updates, publish, promote, rollback, domains, and editors. It's ignored on GET.
  • Creating a project needs no header. source_id is the key, so re-sending the same body returns the existing project with 200. See Projects.
  • Creating an API key (POST /keys) ignores the header, so a new key is never stored or replayed.
  • The key itself is 1 to 200 characters, unique per operation, and scoped to your API account. Derive it from your own job id, such as help-center-sync-0193, so a retry of the same job reuses it.

Responses are kept for 24 hours. A key is bound to the method, the path (including the project id), and the body of its first request. JSON key order and whitespace don't change the match.

Repeat with the same key Result
Same request, first one finished The stored response, byte for byte, with an Idempotent-Replayed: true header. Nothing runs twice.
Same request, first one still running 409 idempotency_in_progress. Retry shortly.
Different body, endpoint, or project 422 idempotency_key_reused. Nothing runs.
First one answered 402, 403, 409, 429, or 5xx Not stored, so the retry runs again. It succeeds once the plan, role, cap, conflict, or limit allows it.

A replayed project create returns the original project_key, so a retry after a dropped response still gets it.
